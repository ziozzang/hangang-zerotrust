## Functional acceptance matrix

- Wrong audience: API-signed token for another audience refuses; no backend. Tampered issuer/SA UID/Pod UID JWTs are invalid proofs and must not pass precheck/TokenReview. Valid tokens for another real SA/Pod produce another verified subject and fail the existing Pum grant. Changing local cluster realm alone changes subject association; it is not an API-attested cluster claim. Wrong fixed API/CA/issuer/namespace configuration fails authentication or grant binding according to that boundary, not a fabricated TokenReview claim.
- Kind collision: same s_hash in legacy users and workload_users with opposite rights. Workload sees only workload_users; Service only users. Delete Workload grant while users retains Allow: new Issue and old permit Observe refuse, output/backend unchanged. Wrong resource/action/class/network/positive minimumAAL refuse.
- Roles: workload client cannot call TokenReview, mint another SA token or mutate policy; reviewer can globally create TokenReview and has only the two namespaced named-object GET permissions above, with no unrelated GET/list/watch/write/secrets access. Explicit SSAR checks require both exact GET positives, unrelated named GET negatives and client/reviewer TokenRequest denial. Withdraw owned reviewer role/binding: new provider exchange refuses. Restore through a newly owned publication/new authentication; old captured proof is never renewed.
- Original evidence: capture before TokenReview, delay provider/sign/output and verify original maximum1s does not restart. Independent SDK contraction can safely refuse a600ms exchange even when raw source has400ms remaining. Never relax product rates or original bounds to make a fixture pass. Record miss, profile/app/key replacement, same-content restore and process restart refuse old observations; fresh proofs can recover.
- Replay: simultaneous/double contract3 consumes exactly one; exact pair after restart remains consumed, signer/key/purpose/nonce identity is shared with strict/Service routes. Wrong endpoint/contract cannot gain another ledger namespace. Admission cleanup is not replay-retention cleanup.
- Withdraw actual bound Pod/SA; measure native TokenReview rejection separately from the original Hop proof deadline. Poll at a bounded interval with an explicit overall timeout (initial design90s), record timestamps/counts without token bytes. Once Kubernetes stops authenticating, no new proof can restore it; previously captured proof still dies at its original ≤1s source deadline. New Pod/SA UID requires fresh verified subject+explicit owner grant, never old grant reuse. Test actual OS process restart separately from same-process owner recreation.
- Final dispatch: delayed connect/TLS/backpressure/expiry/owner replacement after projection must not emit late origin credentials or increment backend counter. Existing raw under-TLS write/vectored/flush irreversible gate remains; already accepted kernel bytes cannot be recalled. An unobserved remote withdrawal is not synchronously discoverable by a local gate.

## Deletion timing and evidence

Kubernetes documentation states pending-deletion bound objects/SAs are rejected at60s or later after deletionTimestamp; nonexistence/UID mismatch also invalidates the binding. The native Hop original1s source age bounds reuse after a successful check, **not total deletion-to-denial latency**. Record API propagation and local source aging as separate measurements, with the exact cluster version and observed result. See [Managing Service Accounts](https://kubernetes.io/docs/reference/access-authn-authz/service-accounts-admin/), [Service Accounts](https://kubernetes.io/docs/concepts/security/service-accounts/) and [TokenRequest API](https://kubernetes.io/docs/reference/kubernetes-api/authentication-resources/token-request-v1/). No instantaneous revocation claim follows the local clock design.
