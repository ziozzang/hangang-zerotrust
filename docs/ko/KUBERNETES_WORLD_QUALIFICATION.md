# 네 서비스 Kubernetes 기능 검증

[English](../KUBERNETES_WORLD_QUALIFICATION.md)

`tools/kubernetes_world_smoke.py`는 고유하게 소유한 네임스페이스에 독립적인
한강·호패·수문장·품계 Deployment/PVC와 호출 수를 세는 테스트 백엔드를 만듭니다.
명시적 kubectl 래퍼·미리 가져온 검증 이미지·호패 테스트 설정·해시 고정 수문장 콘솔·Node 지원
이미지를 제공합니다. 기본 kubeconfig나 클러스터 재생성을 사용하지 않습니다.
합성 자격과 하루 유효 TLS를 만들고 Secret은 stdin으로 전달합니다. 자기 네임스페이스만
정리하며 Retain 정책의 합성 PV는 남습니다.

네 핵심 컨테이너는 UID/GID 65532·읽기 전용 루트·capability 제거·서비스계정 토큰
마운트 없음으로 실행합니다. 판정은 mTLS와 Service DNS를 사용하고 각 소유자가
단일 SQLite 쓰기 PVC를 가집니다. 다중 복제 DB 분산을 의미하지 않습니다.
품계 관리는 HTTPS/mTLS이고 한강 관리는 루프백의 인증된 kubectl 포트포워딩으로
검증합니다. 수문장 관리 Service는 필수 mTLS이며 해시를 고정한 실제 콘솔 플러그인과
범위가 정해진 관리자 자격으로 한강이 위임합니다. 평문 관리 Service는 노출하지 않습니다.
수문장 신호 제출은 이 검증에서 설정하지 않습니다.

한강의 Docker 연결 상태와 설정 SQL은 PVC를 사용합니다. 비루트 초기화 컨테이너가
fsGroup 처리 후 관리자 디렉토리를 0700, DB 파일을 0600으로 준비하며 보호 검사를
끄지 않습니다. 수문장은 재시작 정책 덮어쓰기 대신 최초 생성용 --bootstrap-policy를
사용합니다. 대부분의 준비 상태 검사는 리스너만 확인하므로 실제 보호 요청이 더
강한 기능 합격 조건입니다.

실제 HTTPS 요청·검증된 서비스 신원·자격 소비·메서드/게스트 거부·품계 정책 CAS·
즉시 회수·품계 Pod 교체 후 회수 유지·복구·플러그인 발견과 수문장 관리 mTLS 위임·
관리자 상태를 유지한 한강 Pod 교체·
IP 차단과 수문장 0개 축소 시 거부를 검사합니다. 모든 거부 요청은 실제 백엔드
호출 수를 늘리지 않아야 합니다. 세 판정 모두 gRPC를 사용합니다.

K8s에서 실행되는 선택된 API 서비스 요청 체인의 근거입니다. K8s의 TokenReview/
SubjectAccessReview 위임·모든 메타데이터 원천·일반 리소스 어댑터·전체 브라우저
관리자/공급자·신호 제출·HA·자격/채널 전체 수명·운영 반영·성능은 별도 검증 대상입니다.
격리된 테스트 생성기를 운영 배포 번들로 간주하지 않습니다.

## 실제 브라우저 검증

--browser-probe에 한강의 web/tools/world_admin_browser.mjs를 지정합니다. PATH에
Node가 없으면 --node-binary를 명시하고 Playwright 의존성과 Chromium을 먼저
설치합니다. 자격은 비공개 임시 설정 파일로 전달하며 명령 인수로 전달하지 않고
실패 출력에서도 가립니다. API 가로채기나 UI fixture 서버 없이 실제 포트포워딩된
콘솔에서 첫 로컬 관리자 생성·ID/PW 로그인·품계 게스트 게시·실제 수문장 메뉴의
차단/해제·로그아웃 데이터 초기화를 검사합니다. 이후 실제 요청 회수·Pod 교체·
장애 검증을 진행하고 네임스페이스를 정리합니다.

선택된 로컬 관리자/품계/수문장 화면의 근거이며 호패의 모든 관리 화면·콘솔 연합 SSO·
모든 공급자·운영 관리자 적용은 별도 검증 대상입니다. 브라우저 산출물이나 자격은
게시하지 않습니다.

## 한강 관리자 세션 아래의 호패

--hopae-plugin은 실제 해시 고정 호패 콘솔과 별도 mTLS 관리 Service를 추가합니다.
호패가 명시적으로 한강을 콘솔 권한의 원천으로 선택하며 브라우저는 기존 한강
로컬 관리자 로그인으로 호패 메뉴와 실제 인증 프로필을 조회합니다. 두 번째 호패
로그인은 요구하지 않습니다. 모든 위임 작업에는 범위가 정해진 서명 증명이 필요하고,
수신 서버는 검증된 mTLS와 완전히 검증된 위임이 함께 있는 요청에 한해 실제 접속자
하나만 신뢰합니다. 전역 프록시 신뢰 대역을 바꾸지 않고 서명 없는 TLS는 기존
프록시/네이티브 권한 검사를 유지합니다. 원격 관리/프로필 조회의 근거이며 연합 로그인·
모든 공급자/변경 화면의 완료는 아닙니다. 데이터 평면의 인증은 계속 호패가 소유합니다.

실제 프로필 편집기에서 비활성 설정을 게시하면 보호 요청이 401로 거부되고
백엔드 호출 수가 늘지 않는 것을 검증한다. 원래 설정을 다시 게시하면 200으로
복구된다. 테스트 CA와 실제 한강 요청 경로를 사용하며 API 응답을 가로채지 않는다.
이 근거는 프로필 회수·복구를 포함하지만 모든 공급자 변경 화면의 완료는 아니다.

프로필 회수 후 초기 설정을 그대로 둔 채 실제 호패 Pod를 교체한다. 다시 조회한
설정도 null이며 보호 요청은 401이어야 한다. 재연결 중 관측한 응답은 401 또는
503만 허용하고 복구 이전의 200은 실패다. Pod 교체는 명시적 kubectl 래퍼로
소유한 테스트 Namespace의 deployment/hopae만 대상으로 한다. 탭 조회 완료를
확인한 뒤 다시 편집하며 고정 대기 시간으로 화면 준비를 추정하지 않는다.

## 동시 관리자 게시

별도 브라우저 컨텍스트에서 실제 계정으로 다시 로그인하고 호패의 원래 리비전을
조회한다. 첫 세션이 회수한 뒤 두 번째 세션의 낡은 문서를 실제 편집기로 게시하면
실제 응답 409, 화면 오류와 기존 리비전 유지, 보호 요청 401 및 백엔드 미호출을
요구한다. 세션 저장소·자격·API 응답을 주입하지 않는다. 콘솔 위임과 DB 원천을
통과하는 덮어쓰기 방지 검사이며 관리자 역할 분리의 검증을 대신하지 않는다.

## 공용 런타임 패키지 리비전 검증

런타임 819177c(0.1.2)를 고정한 호패 6eb07d3·수문장 5de28f3·품계 200ed48의
정적 nonroot 이미지로 실제 브라우저/월드 테스트가 종료 코드 0으로 통과했다.
패키징 전에 실제 네이티브/gRPC 네 프로세스 체인을 검증하고 아카이브 전송
체크섬 일치 및 두 노드 import를 확인했다. 소유 Namespace는 삭제했고 합성
PV는 기존 Retain 정책대로 유지했다. 선택된 gRPC 데이터 평면·관리 mTLS·독립
로그인/낡은 게시 거부·프로필 회수/복구·호패 Pod 교체·품계 영속 회수/교체·
한강 상태 보존·네트워크 원천 장애를 포함한다. 기존 Ingress와 운영 서비스도
정상이다. 테스트 클러스터 패키지 검증이며 운영 반영·모든 네이티브 배포 모드·
전체 성능 검증까지 완료한 것은 아니다.

## 서비스 전용 혼합 구성 검증

`--composition --observed --credential-projection`은 네 production owner와 테스트
백엔드에 독립된 다섯 번째 인증 relay Pod를 추가합니다. 기본은 명시적인 All이며
`--composition-mode any`로 Any를 선택합니다. 고정 호패 프로필이 로컬 API 키와
HTTPS relay slot 및 정확한 Service 신원 관계를 선언합니다. Namespace 소유 CA를
`api_relay.ca_file`로 mount하고 정확한 Service DNS 인증서를 검증합니다. 인증서/
서버이름 검증은 유지합니다. Relay Secret 환경에는 원격 키 둘과 fixture 제어 키만,
호패에는 로컬 키만 전달하며 원격 provider 키를 전달하지 않습니다.

요청은 제한된 envelope payload의 Hopae-Compose를 사용합니다. 독립 receipt probe는
고정 credential_scheme=hopae_compose 설정과 credential 환경의 payload만 사용하고
기존 모드의 Bearer 기본값을 유지해야 합니다. 실제 issue, 독립 observation, 소비형
refresh와 최종 검사가 필수입니다. 누락/제시된 실패/서로 다른 검증 신원 거부, relay
circuit 개방과 명시적 source Pod 교체 복구를 검사합니다. 모든 거부에서 backend
count가 같아야 하며 성공 응답에는 별도 origin 키만 있고 provider 키 둘/envelope/
native caller 키는 없어야 합니다.

AAL0의 Service 혼합 구성 범위입니다. Human MFA, Workload 혼합, 로컬 계정 복구,
streaming 또는 임의 배포 구조를 검증했다는 뜻은 아닙니다. 기본 모드는 기존 네
production owner를 유지하며 relay 키/Pod/혼합 설정을 만들지 않습니다.
