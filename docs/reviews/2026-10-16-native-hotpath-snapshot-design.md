## Snapshot candidates versus obligations

1. **Safe metadata snapshot candidate:** Store realm+nonreusedUserID canonical coordinate is deterministic public data. Cache/retain it in an actual owner snapshot keyed by exactStore/incarnation+issuer+UID; no SQL `admin_human_subject` lookup on each native Verify is intrinsically required once a current authenticated user/session is established. Disable/current eligibility remains independently fenced; do not let a cached coordinate establish primary/MFA or resurrect deleted users. Admin legacyunsupportedID omission remains separate from native strictness.
2. **Native Human current snapshot candidate (substantial work):** session/handle/termination, userstatus/credential/authz/groups, primary provenance/provider material/config generations, TOTP enrollment/factor generations, native realm/reservations can be read from immutable in-memory source snapshots. This requires ALL legitimate mutations to publish/invalidate through the same actualStore owner, including logout, userdisable, credentialrotation, primaryreauth, factorremove/downgrade, directory/provider/config/material replacement and source failure. A bounded recordmap is not this source snapshot.
3. **Durable replay is not ordinary cacheable policy:** both proofs must be consumed atomically and remain nonreplayable through crash/restart/rollback according to existing canonicalledger. No eviction of still-retained ID, no nowUTC reconstruction, no source TTLrenewal, no per-Humanledger. Samewriter current must remain consistent with real durable mutation ordering; removing redundant READS cannot detach it from commit.
4. **Publication gaps:** marking a new snapshot current before DBcommit grants on rollback; publishing only aftercommit without an earlier withdrawal barrier lets old owner survive committedrevoke. Required design is a failclosed mutation/pendinggeneration barrier before durability, commit/validate, immutable publication, then readiness. Every old capture retains original owner/generation/deadline and cannot adopt a newer snapshot. Failed mutation/publication cannot silently reenable a retired old capture. Cold restart hydrates from verified DB before readiness; missing/corrupt/gapped state refuses. No snapshot sharing across merely identical filenames/DBclones.
5. **Distributed scope:** local Arc identity and one SQLite writer are not crossprocessDB desired-material authority. ExternalDBMS/follower support needs monotonic fencing/commit/freshness and explicit recovery semantics; this audit does not invent those capabilities.

## M1 mutation publication contract and executable test matrix

Inventory every legitimate Store writer before enabling a snapshot read path. Session handle creation/rotation/logout/termination and idle/absolute expiry; primary reauthentication and identity linking; user status/credential/authz/group changes; TOTP prepare/confirm/remove and factor downgrade; provider enable/delete/revision/material/realm/config publication all affect different current predicates. An omitted writer is a security bug, not a tolerated stale-cache window. All generations are checked/monotonic with explicit overflow refusal. A snapshot lookup must be O(1)-like over bounded keys; do not clone all session records on each Issue.

The proposed local single-owner state machine is `eligible(old generation) → pending/ineligible → durable commit → verified immutable publication(new generation)`. Old captured source generations are never rebound to new snapshots. Pending failure leaves readiness closed or requires a separately validated fresh recovery publication. Do not return to an already retired old capture merely because the transaction rolled back. A no-op mutation can only preserve current ownership under an explicit same-content/same-generation contract, not by comparing convenient field subsets.

| Deterministic test | Required refusal / evidence |
|---|---|
| Pause writer after pending barrier, before SQL; concurrently Observe retained proof | Old proof refuses without source-age renewal; no fallback succeeds while pending. |
| Commit logout/userdisable/TOTPremove, pause before snapshot swap | Observe and H4 final writer refuse; committed withdrawal cannot wait for a healthy old snapshot to expire. |
| Roll back SQL after pending barrier | No new generation or grant becomes visible; old retired capture remains retired; recovery is an explicit validated publication. |
| Crash before commit, after commit/before publish, after publish/before acknowledgement | Actual child restart hydrates verified committed state before readiness. Lost acknowledgement is idempotently reconciled; it does not imply rollback or double publication. |
| Competing unchanged and changed publication, delayed old completion, A→B→A material/config | Exact prepared-generation CAS, same Store/application ownership and late retirement guards refuse stale/ABA publication. |
| Expiry during callback/SQL/queued writer, suspend-aware elapsed jump, clockread failure or true reversal | Same original anchor and domain; failed owner irreversibly refuses. Reverse completion of healthy concurrent reads must not falsely latch rollback. |
| Native oracle comparison for AAL1/AAL2, group/class/scope variations | Snapshot verdict/facts equal existing joined SQL for actual provider/session/factor provenance. No current user revision is compared to a global user floor. |
| Same proof against foreign Store/realm/snapshot, missing record, ordinary generic session | Refuse; identical user labels/config or a raw metadata object are insufficient. |
| Cancellation/lost response while canonical pair writer queued or committed | Before commit, guard rolls back; after commit, pair can be burned but not reusable. Same canonical table across classes; full signed retention is not shortened to admission. |
| Stale/corrupt/gapped hydration or source stream/relist gap | Fail startup/readiness, no serving an optimistic empty/default snapshot. |

**Database restore and distributed limitation:** a generation stored only inside a DB cannot detect an out-of-band rollback of that entire DB to an older internally consistent backup. Realm/random IDs do not detect live clones. An automatic antirollback guarantee requires an independently trusted monotonic epoch/checkpoint or a documented external recovery procedure that retires old signing/source/session domains before service readiness. M1 must explicitly choose and test its supported restore boundary; do not claim arbitrary privileged SQL tamper/clone protection or distributed linearizability. Until such a mechanism exists, out-of-band restore/multiwriter access is outside the single-owner contract and requires stopped-service recovery. External DBMS/follower desired-state ownership remains a separate milestone.

## M2 prepared actual bytes, not a digest capability

Use the existing SDK actual-body preparation exactly once per final selected request. Retain its private immutable prepared request plus digest/body-hash data with the same compiled Scope, original frontend verification context and owned Bytes. Route capture and final comparison consume those data, rather than rehashing the same body before SDK.prepare. Scope fingerprints may be cached at immutable configuration compilation. No public `prepare_from_digest`, numeric Observation factory or caller-provided hash can replace actual-body preparation. Header absence versus empty, duplicate rejection, method/path/query, destination and both revisions remain exact. Final URI/header/projection-slot/framing seal and transport owner checks are not removed.

Required M2 tests: existing v1 bytevectors unchanged; all independent H1v2 vectors unchanged; empty/nonempty/same-length mutation, fragmented versus singleframe body, trailers/overlength/slowbody, bound header absent/empty/duplicate/control, forwarded authority versus selected origin, stale route revision and both valid scope variants. An owned body buffer cannot be modified after preparation; no retry or output callback gets a mutable alias. Actual final backend receives exactly one expected body SHA. Instrumented bodyhash invocation count becomes one for a successful Human preparation without reinterpreting any proof data as authentication authority.

## Accounting before performance claims

Add low-cardinality, bounded, test-only accounting at owned function boundaries: native durable read transactions/statements; reader-pool reuse/open; writer queue wait and transaction/commit counts; outgoing method-class RPC counts; body bytes collected/copied and hash passes; fixed-scope digest computations; bounded record/quota occupancy; cancellation/failure stages. Do not log token/header values, cookies, user IDs, request bodies or full contexts. Avoid a global contended per-step counter on a production100k path without measurement; test counters and optional sampling must not add arbitrary callbacks after the final SQL/time fence.

First record one exact-source functional run with every counter attributed to its layer; identify conditional provider/AAL cases rather than inventing a universal constant. Then compare M1/M2 to that baseline under identical artifacts and inputs, with allocation/memory bounds and tail-latency measurement separated from SQL/RPC counts. A benchmark must state hardware, versions, concurrency, body/frame sizes, provider/network behavior, duration, failures, durable commit policy and clock/source semantics. Functional priorities remain first. A bounded map, a synthetic signer peer or an isolated in-memory microbenchmark is not evidence for full-chain100kRPS or production zeroSQL.

## Adoption gates

Keep legacy Service/Workload/generic mode wire and behavior unchanged. Freeze each source milestone with independent exact-hash review, actual provider/native/pair/backend gates, default+feature workspace and strict checks appropriate to the changed owners. Publish dependency pins atomically only after qualification; never substitute a local path patch to mask nominal DTO mismatch. No release/adoption or performance claim is authorized by this design alone.
